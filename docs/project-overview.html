01 / topology

One public edge, layered security, isolated ownership

Web and Mobile clients use the API Gateway only. Internal service calls are explicit and protected; persistence stays behind each service boundary. RabbitMQ carries domain events without carrying raw Document or Comment content.

WEB → GATEWAY → SERVICES → DATA
sync HTTP async RabbitMQ database ownership ▣ protected / internal-only path
Boundary contract: Clients receive API DTOs and one-time download responses. They never receive object_key, storage credentials, KEKs, internal endpoint access, or raw infrastructure connections.

Database ownership

No cross-service foreign keys, shared Prisma repositories, or database reads. Synchronize through internal APIs and domain events.

Event discipline

RabbitMQ envelopes carry IDs, decisions, and metadata—not raw Document bytes or Comment content. Consumers are retryable and idempotent.

Audit topology

The Audit Log runs as exactly one replica and has one writer; chain-head locking and event_id deduplication prevent the chain from forking.

03 / behavior

Core workflows, end to end

These paths show where authorization is decided, where content is allowed to exist, and how evidence and notifications follow the business action.

REQUEST → DECISION → EVIDENCE
03.01 · AUTHORIZATIONAuthentication and account control

Public auth routes enter through the Gateway; identity state is owned by Authentication & Identity, with session metadata in Redis.

  1. Register — public registration creates an EMPLOYEE; ADMIN cannot be self-created through this route.
  2. Login — credentials are checked; a locked account is denied; success issues a short-lived access token and refresh token.
  3. Refresh — the refresh token is validated, rotated, and the old token is revoked; a locked account cannot refresh.
  4. Logout — the refresh token is revoked and the Redis session is removed.
  5. Lock / unlock — User-Role Management changes account state; security lock policy revokes all active refresh sessions through a protected internal path.
03.02 · AUTHORIZATIONTask participation and confidentiality

Task access is per-task and deny-by-default. A Participant is the Creator, current Assignee, or explicitly assigned EMPLOYEE.

  1. Assign — Task Management checks the caller and records the participant on this specific Task.
  2. Read — direct Participants may read the task, Comments, submissions, review decisions, and Task Activity.
  3. Contain — mentions, subscriptions, and notification recipients never create access; an ADMIN can never become a Participant.
  4. Oversight — an ancestor Creator or current Assignee can see only descendant summary fields: title, status, assignee, deadline, overdue, and result.
03.03 · AUTHORIZATIONTask-to-Grant authorization

Every ordinary Document Grant has a mandatory source_task_id. Permission Service decides against its own permission_db only.

  1. Create — an ADMIN administers the primary Grant for an EMPLOYEE; the Grant names the Document, actions, Task, and explicit expiry.
  2. Compute — effective_expires_at = min(grant expiry, task deadline, parent effective expiry), then store it on the Grant.
  3. Check — every content, Comment, and archive action calls POST /internal/permissions/check; a missing Grant, expiry, Revocation, or missing action denies.
  4. Delegate — a child Grant is a permission subset, cannot outlive its parent, and requires the right to share.
  5. Revoke — deliberate Revocation, parent Revocation, or Effective Expiry cascades to descendants; extending a Task never widens an existing Grant.
03.04 · CONTENT SECURITYUpload through the Security Pipeline

A file becomes a Document only after the one-way pipeline succeeds. State-secret material is rejected before a Document row or object is created.

scan→checksum→encrypt→sign→store
  1. Stream — Gateway forwards the multipart stream to Document Management, which validates size, MIME type, and state-secret declaration.
  2. Scan — Document Security writes transient plaintext and scans it with ClamAV; failures clean up and stop.
  3. Checksum — SHA-256 is calculated over plaintext. A random per-version DEK encrypts with AES-256-GCM.
  4. Protect — the DEK is wrapped by the active versioned KEK; metadata is signed; only ciphertext is sent to MinIO.
  5. Record — the encrypted record stores checksum, signature, wrapped DEK, IV, auth tag, KEK version, and object metadata; transient plaintext is removed in finally.
03.05 · CONTENT SECURITYTicketed download and redemption

Download is a two-step, single-use capability. A ticket never bypasses authorization and cannot outlive the Grant’s Effective Expiry.

  1. Request ticket — Document Management calls Permission Service for DOWNLOAD; denial is audited. On allow, create a ticket capped by ticket expiry and effective_expires_at.
  2. Redeem — Gateway routes the ticket to Document Management, which checks actor, Document, version, unused state, and ticket expiry.
  3. Verify — Document Security verifies the metadata signature, reads ciphertext from MinIO, unwraps the versioned DEK, decrypts, and rechecks SHA-256.
  4. Deliver — plaintext streams back through the Gateway; the ticket is marked used and the redemption is audited. Clients never see storage paths.
03.06 · EVIDENCEAudit, notifications, and monitoring

The same domain event can feed user-facing Task Activity, the evidence ledger, notifications, and security rules—each with a distinct owner and purpose.

  1. Audit append — allow and deny decisions append to the single-writer, hash-chained Audit Trail. Raw Document and Comment content never enters the event.
  2. Chain verification — Audit Log checks each event hash in sequence against the prior hash and returns the first broken position as broken_at when integrity fails.
  3. Notify — Notification consumes RabbitMQ events for assignment, sharing, review, expiry, and security notices. Delivery does not grant access.
  4. Monitor — Security Monitoring records events and evaluates configurable thresholds for failed login, denied access, abnormal download/share, expiry access, invalid integrity, and archive rejection.
  5. Respond — an alert can trigger policy-driven account lock and refresh-session revocation; ADMIN manages rules and alerts, not content.
03.07 · ARCHIVERecords and Transfer Packages

Archive actions are content-adjacent capabilities held by EMPLOYEEs. The submitter and Archivist are separated by policy.

  1. Assemble — Document Management groups Document versions into a closed Record; the Record is sealed when complete.
  2. Package — create a signed Transfer Package with manifest, metadata, per-file checksums, signature data, Audit references, and handover receipt.
  3. Submit — ARCHIVE_SUBMIT plus TRANSFER authorization moves the package through DRAFT → SEALED → SUBMITTED.
  4. Receive and verify — an EMPLOYEE Archivist holding ARCHIVE_RECEIVE checks files, malware state, checksums, signatures, metadata, and separation of duties.
  5. Accept or reject — valid packages become ACCEPTED → ARCHIVED; invalid packages record a rejection reason and remain evidenced.
03.08 · ARCHIVERetention and controlled Disposal

Retention eligibility is not an immediate delete. Disposal destroys stored content only after policy, holds, permission, and approval are satisfied.

  1. Check eligibility — the idempotent retention worker identifies an archived Document whose retention period has ended.
  2. Respect holds — an active retention hold prevents eligibility from progressing; releasing it is itself controlled and audited.
  3. Approve — a qualified EMPLOYEE with DISPOSAL_APPROVE authorizes the controlled action; an ADMIN cannot approve Disposal.
  4. Execute — the approved path removes stored Document content according to policy, without deleting the Audit Trail.
  5. Evidence — Disposal and its approval remain in the hash-chained evidence record, and notifications carry no sensitive content.

04 / non-negotiables

Security invariants

These rules are architectural constraints, not UI conventions. A failure to prove an allow is a denial.

DENY BY DEFAULT
01

ADMIN governs, never reads

ADMIN manages users, roles, capabilities, policies, and alerts. ADMIN never accesses Document or Task content, cannot hold content-adjacent capability, and can never become a Participant.

02

EMPLOYEE participates in content

EMPLOYEE is the only role that can participate in Tasks or hold Document Grants. Participation, Grants, and capabilities are separate decisions with explicit scope.

03

Fail closed

Permission Service is the hard dependency for content. Timeout, connection refusal, malformed input, or 5xx returns PERMISSION_SERVICE_UNAVAILABLE and never an allow-cache.

04

Effective expiry wins

A Grant dies at the earliest of its own expiry, Task deadline, or parent Effective Expiry. Request-time checks remain authoritative; deadline extension cannot restore access.

05

One writer for evidence

Audit appends are serialized under the chain-head lock. The unique event_id check stays inside that transaction so RabbitMQ redelivery cannot fork the Audit Trail.

06

Ciphertext only at rest

Plaintext exists only transiently inside the Security Pipeline. MinIO stores ciphertext; PostgreSQL stores metadata. Signatures and checksums are verified before plaintext delivery.

07

Gateway-only clients

Web and Mobile call the Gateway only. They never call internal service ports, /internal/* endpoints, databases, Redis, RabbitMQ, MinIO, or ClamAV.

08

Evidence is not content

Audit events and notification payloads may identify an action and its decision, but never contain raw Document bytes, Comment content, storage secrets, or KEKs.

09

Disposal preserves proof

Retention and controlled Disposal can remove stored content after approval, but the Audit Trail survives. The evidence of what happened is not disposable content.

Operational shorthand: if an authorization decision cannot be proven from the owning service’s current state and protected contracts, the platform denies it, records the decision, and lets monitoring evaluate the signal.
